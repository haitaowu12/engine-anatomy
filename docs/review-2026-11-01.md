# Engine Anatomy: depth and inspection review

**Status:** the initial bounded review below is retained as historical evidence. The subsequent authorized full implementation is recorded in the Version 3 response at the end and in `PRODUCTION.md`. Statements below about unfinished first-layer work describe that earlier phase.

## Evidence and revision

Baseline: [`67d8c962454dac1fa932d4c91cc6280e7d8d44b6`](https://github.com/haitaowu12/engine-anatomy/tree/67d8c962454dac1fa932d4c91cc6280e7d8d44b6), which merged PR #4, Midnight Brass. The README identifies GitHub Pages as the current public release and the GPT Site as a previous release. These destinations should not be treated as identical without comparing their build identifiers.

This review inspected the current source, component manifest, three numerical plants, guided lessons and tests. It is not a practitioner trial or a successful hardware-WebGL visual audit. The available cloud browser reports WebGL disabled and displays the 2D fallback; therefore no claim that the normal 3D rendering or this new inspection view was visually accepted is made. Scene-graph tests, where recorded, test real Three.js geometry with a stub display and controls rather than GPU pixels.

## Why the gap occurred

The existing product built a semantic atlas and running teaching model, while its geometric authoring remained a common schematic. This is a useful foundation, but it does not produce detailed anatomy by adding more component descriptions or changing the theme.

| Finding in the baseline | Evidence | Consequence |
|---|---|---|
| No exploded-view state existed | `src/renderer.js` exposed selection, lenses, isolation, cutaway, focus and camera actions. `docs/DESIGN.md` explicitly prohibited stretching/exploding mechanical shafts. | The user could open a fixed cutaway or hide parts, but could not progressively inspect layers. Protecting shaft continuity was appropriate; prohibiting all separations was too broad. |
| All engine families share one short procedural core builder | `buildEngine()` in `src/renderer.js`; fixed row counts, profiles and dimensions selected mainly by fan/prop booleans | Differences in architecture are represented, but repeated geometry reaches its detail limit when zoomed. No per-stage identity or deep subassembly exists. |
| Blade-row hubs were solid disks | `row()` used a filled `CylinderGeometry` for rotors and stators | In the concentric configurations, HP/Ng disks occupied the inner shaft passage; stationary hubs also crossed the shafts. The inset's stated clearance was not consistently represented in the main mesh. |
| Casing and stator identities were conflated | Compressor shell used `compressor.stator`; turbine closing shell used `turbine.vanes` | Inspecting, separating or explaining casing versus vane rows could not work independently. |
| Material and lighting vocabulary is narrow | One default `MeshStandardMaterial` family, hemisphere/directional lights, no environment reflection or contact-shadow pipeline | Metallic highlights alone cannot explain materials or shapes; large shells, supports and detail parts tend to share a visual response. |
| Fine details are schematic substitutes | Box-shaped prop/rotor blades, generic square gear teeth, torus bearings, sphere markings on liners, tiny boxes for uncoded components | Additional labels do not turn these substitutes into inspectable mechanisms. The model needs authored geometry at the learning scale. |
| Text depth exceeds geometry depth | The manifest explains bearings, lubrication, fuel control, health, channels and configuration-dependent services; the renderer often places a proxy box | Selecting an advanced item frequently opens an explanation rather than a mechanism the learner can inspect. That distinction should be explicit and should guide modeling priorities. |
| Labels lack an occlusion/packing system | Selected and event labels project one fixed anchor, clamp to the viewport and have no general collision/occlusion handling | Zoom/orbit/nearby highlights can sever the perceived relationship between label and component. A single focused label is not a scalable labeling system. |
| The fallback is a separate, reduced representation | `src/schematic.js` selects one related interface edge for control/services and uses broad component blocks | It keeps a learning route available, but it does not reproduce detailed anatomy or the complete selected signal branch. Its success cannot qualify 3D quality. |

The numerical core is stronger than the appearance suggests. It already distinguishes independent spools, fan/core streams, controller request from metered fuel, calculated T4 from located temperature probes, separate propeller speed control, and explanatory services from simulated loops. Preserve those distinctions while improving geometry. The test suite verifies the declared synthetic equations and topology; it does not validate a manufacturer engine.

## Corrections implemented in this change

1. Added a staged exploded-inspection control. Outer casing sectors separate first; combustor liner sectors follow. Radial guide lines retain correspondence. Every separated sector spans no more than 180 degrees, so its radial translation increases clearance from the shaft axis.
2. Preserved shafts, rotors, vanes, bearings and their semantic membership. The running model pauses during inspection. Reassembly restores its prior pause state. Architecture changes and new trials reset inspection.
3. Added separate compressor and turbine casing components, preserving the distinction between a pressure shell and stationary blade rows.
4. Replaced conflicting filled hubs with annular geometry where an independent shaft or stationary-row clearance is required. The outer shaft now has an explicit annular bore. Removed inner-shaft collars/keys whose full axial envelope would enter that passage, and moved the accessory takeoff to the outer-shaft surface. Actual transformed-mesh tests check the complete independent-spool envelope, not just a nominal shaft radius.
5. Made selected-shell anchors/focus follow displaced shell geometry while keeping incidental inspection changes from moving the camera. Return view keeps its existing explicit behavior.
6. Corrected isolation visibility: non-shaft selections could assign `undefined` to other groups instead of strict `false`, which Three.js does not treat as hidden. Real scene-graph regression tests now exercise this case.
7. Removed stale trial-event highlights when manual inputs cancel a guided trial, and stopped describing every manual transient as a settled baseline.

These are bounded corrections. They do not complete component-detail authoring, physically accurate gear contact, full CAD assemblies, a general occlusion-aware label system, a material/environment-lighting pass or the complete curriculum. Inspection uses declared instructional sector splits; it is not a maintenance procedure.

## Content and view consolidation

Keep one common anatomy for the compressor, combustor, turbine, shaft support and services, with explicit architecture variants. Avoid duplicating the same introductory explanation across three engine tabs. Preserve distinct numerical plants and true mechanical differences.

Use three coordinated views of the same component IDs:

- **Where it is:** aircraft context, installation, engine module, assembly and detail. Use geometric cutaways and inspection only where spatial relationships matter.
- **What it does:** gas, heat, work and shaft-load paths. Coordinate 3D highlighting with a station diagram and a qualitative or explicitly synthetic thermodynamic plot.
- **How it responds:** demand, sensing, controller, actuator, plant and load. Use the 2D signal graph for causality and the 3D scene for sensor/actuator locations. Keep guided trials alongside the diagram and model.

Compare architectures at matched learning tasks: what the power turbine drives, how shaft speed differs from load speed, which controller acts on fuel or blade pitch, and where useful thrust or shaft power appears. Changing a family should preserve the selected concept where it exists and explain its absence otherwise.

## Detail to add, in order

| Priority | Assembly / lesson | Required visible or conceptual detail | Keep explicit |
|---|---|---|---|
| 1 | Compressor stage | Separate rotor/stator rows, annular flow passage, blade curvature, disk attachment, casing support, tip/root clearance, selected-stage work | Stage counts and dimensions are illustrative; geometry alone is not a CFD solution. |
| 1 | Combustor | Outer case, liner, air-admission/dilution paths, fuel manifold/injectors, swirl/primary-zone concept, ignition location | Flame/air distribution is conceptual; configuration variants have their own sources. |
| 1 | Turbine and spools | NGV, rotor, shaft/disk coupling, bearings/support frames, independent concentric clearance, stator/rotor distinction | Do not animate fixed vanes or join independent shafts. Cooling and seals need their own source-backed details. |
| 2 | Output mechanisms | Helicopter reduction/freewheel/main and tail paths; turboprop reduction and pitch hub/PCU; fan/core torque paths | Free turbine and freewheel are distinct concepts; generic gearing is not a production design. |
| 2 | Service circuits | Fuel supply/metering/return as applicable; oil pressure/scavenge/filter/cooler/breather; starter/generator/bus | Model a whole selected representative circuit; do not pretend every engine uses one configuration. |
| 2 | Control and sensing | Complete directed loop, sensor location, quantity, units, measured versus inferred value, limit/monitor roles | Monitoring is not automatically control feedback. Public examples do not disclose production control schedules. |
| 3 | Alternatives and operating states | Axial/centrifugal compression, forward/reverse flow, direct/geared fan as comparisons; starting and shutdown as sourced causal lessons | Current numerical models do not simulate start/stop, surge, feather/reverse, real fault response or six-DOF flight. New simulations require declared equations and validation. |

## Acceptance gates for a detailed end state

- A learner can trace the selected mechanical path from turbine to load and explain why the independent spool is not mechanically coupled to it.
- Every part promised by a detail view is selectable and has rendered geometry at that view's inspection scale; proxy-only entries are identified as explanations.
- Exploded, cutaway and assembled states preserve component identity and return to the same transforms; no shaft stretches, detached sensor claims or hidden whole-model reset occurs.
- Every supported architecture has a physical-bounds/topology check for shaft passages, stationary clearance and required parts, separate from numerical tests.
- Accepted desktop screenshots must show assembled and maximally separated states, near/far selection, isolation, a complete mechanical route, control-branch context and reassembly. The camera and labels must not crop the selected assembly, overlap its explanation or imply a connection to an occluded part.
- A fallback test and normal-WebGL test are recorded separately. A fallback success cannot stand in for a render test.
- Content changes identify their primary source, configuration scope and whether a value is measured, calculated, synthetic or explanatory. Source rights and model-asset provenance remain separate fields.
- Performance must be measured on a named browser/device and representative detailed scene before adding global postprocessing. Establish a frame-time and download-size budget from that measurement; do not claim a universal device target without testing it.

## Public primary references used to check the direction

- [NASA Glenn: two-spool turbofan](https://www.grc.nasa.gov/www/k-12/airplane/Animation/turbtyp/etfh.html): independent concentric fan/core shafts and separate flow streams.
- [NASA Glenn: axial compressors](https://www.grc.nasa.gov/www/k-12/VirtualAero/BottleRocket/airplane/caxial.html): rotor/stator roles, casing support and limits of simplified aerodynamic depictions.
- [NASA Glenn: propeller thrust](https://www.grc.nasa.gov/www/k-12/airplane/propth.html): rotating airfoils, twist and the limitations of ideal momentum estimates.
- [NASA Glenn: Brayton cycle](https://www.grc.nasa.gov/www/k-12/airplane/brayton.html): compression, heat addition and expansion as coordinated learning concepts.
- [FAA: Helicopter Instructor's Handbook](https://www.faa.gov/sites/faa.gov/files/regulations_policies/handbooks_manuals/aviation/FAA-H-8083-4.pdf): freewheel function distinct from engine torque generation. The public source provides concept support, not permission to depict a specific engine's maintenance procedure.

No reference artwork, proprietary geometry or calibrated engine data was copied.


## Version 3 response to the full implementation request

Starting from `a7640c6cd5bd167188d658a13cbfc8b1dd65934c`, the application implements the roadmap's generic teaching scope rather than leaving it as a list of recommendations. The numerical plants remain intact. Actual source additions now provide:

- Stage-level rotor/stator/disc identities, cambered/twisted blade surfaces, support frames and explicit shaft passages.
- Perforated combustor liner geometry, dome/swirlers, primary/dilution features, cooling lips, injector manifold/tips and guided combustion explanation.
- Turbine discs/NGV identities, bearing races/elements/housings and seal details.
- Separate helicopter freewheel/main/tail and turboprop reduction/pitch mechanisms. The selected planetary tooth counts satisfy the original 12:1 and 10:1 model ratios.
- Fuel supply/bypass, oil pressure/bearing/scavenge/relief/breather, electric/pneumatic starting and ignition construction, with complete route/branch navigation.
- Shared concept/instance/parent relationships, target recipes, ancestry-aware isolation, geometry-based focus and leader/occlusion-aware label placement.
- Coordinated anatomy, gas/heat/work, control and service views; walkthroughs separate from numerical experiments; matched architecture comparisons with explicit alternative diagrams.
- Differentiated WebGL materials, procedural environment/contact depth, static batching, quality caps and a real-geometry SVG fallback using pinned Three modules.

The causal display now uses existing shaft work balances; it does not invent stage pressures or service measurements. Detail and correctness are separate gates: real-triangle envelope tests continue to protect the independent shaft passage, and additional tests check all leaf construction, all-recipe reset, true liner ports, fixed-ring reduction kinematics and graph/lesson completeness. Browser evidence must identify the actual backend/build. A working SVG projection is not a hardware-WebGL appearance claim.

This closes the geometric-authoring, inspection-state, component-identity, curriculum-consolidation and unsupported-fallback gaps identified above for the declared generic product. Remaining boundaries are engineering scope: manufacturer-specific CAD, validated engine maps/CFD, thermal/stress/life analysis, actual maintenance disassembly, real faults/start/stop and flight dynamics are not claimed. See `PRODUCTION.md` and the current `VERIFICATION.md` section for exact implementation and acceptance.
